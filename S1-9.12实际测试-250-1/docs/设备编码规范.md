# Snappy v1 设备编码规范

## 1. 目的

本文规定 snappy 仓库中设备、总线、控制链路及其 fake 实现的编码要求，用于保证：

- 真实硬件资料未确认时，代码保持可编译、可测试且不会误驱动设备；
- CAN、RS485、继电器、传感器、G20 UDP、MQTT/TLS 使用一致的分层、命名、错误和测试模型；
- 设备协议参数可以追溯到确定的型号、资料版本、页码或章节；
- 安全停止、链路接管和执行器状态不会因实现语言或具体驱动不同而产生歧义；
- fake、unconfigured 与 real 后端遵守同一契约，但不会互相伪装或静默降级。

本文面向设备驱动、控制程序、网关、Android/G20 适配器、云端工具、契约、配置、测试和部署代码的维护者。

逐设备帧、寄存器、量纲、配置门禁和硬件在环要求见 [设备驱动开发规范](设备驱动开发规范.md)。两份规范必须同时满足；发现冲突时应先修正文档，禁止在代码中自行解释。

## 2. 规范用语

本文使用以下规范性关键词：

- **MUST / 必须**：不可违反；违反即不允许合并、发布或声明完成。
- **MUST NOT / 禁止**：明确不允许。
- **SHOULD / 应**：默认必须遵循；只有存在可说明、可评审的技术理由时才可偏离，并须记录理由和替代验证。
- **SHOULD NOT / 不应**：默认禁止；偏离时须记录理由和风险控制。
- **MAY / 可以**：可选做法，不影响合规性。

“现有规则”表示当前仓库设计或代码已经确立、后续实现必须继续遵守的边界；“目标规则”表示从现在起新增或修改代码必须达到的规范；“当前差距”表示审计时尚未实现或尚未统一的内容，不得据此声称仓库已经具备对应能力。

本文的 MUST 对新增代码、被直接修改的接口/行为/配置/测试，以及本次交付所声明完成的范围立即生效。第 19 节列出的未触及既有差距属于遗留问题，不因本文发布而自动阻止所有无关变更，但任何变更都禁止新增、复制或扩大差距。若任务没有授权处理相邻遗留问题，可以保持未修改部分的现状，但必须如实记录影响，且不得把该遗留能力声明为完成。涉及安全停止、实际 arm、对外契约兼容或启用 real 后端的 MUST 不适用遗留豁免。

## 3. 适用范围与权威顺序

### 3.1 适用范围

本文适用于：

- `rk3588/control`、`rk3588/gateway`、`rk3588/drivers`；
- `simulator/fake-hardware`、`simulator/fake-g20`、`simulator/fake-mqtt`；
- `remote/android` 中的协议和 G20 适配器；
- `cloud` 中的命令构造、消息接收、存储和 MQTT 边界；
- `contracts/vN` 中的 JSON Schema 与测试向量，包括后续协议版本；
- `rk3588/config`、部署模板和相关测试；
- 从本地、Git 忽略的 `exa/` 原厂资料或示例转化而来的正式实现。

`exa/` 内原厂手册、SDK 和示例属于协议证据与参考材料，不自动符合本文编码规范，也不得因“厂商示例可以运行”而直接进入正式构建目标。

### 3.2 权威顺序

发生冲突时，必须先判断冲突属于哪一种事实，再按以下顺序处理：

1. 用户已确认的安全与产品架构决策，以 [`docs/snappy v1 精简架构设计.md`](snappy%20v1%20精简架构设计.md) 为准。
2. 设备协议事实以对应型号、版本明确的原厂资料为准；汇总文档不得覆盖原厂资料中的确定事实。
3. `docs/设备驱动开发规范.md` 规定 Snappy 已批准的设备 profile、可用协议子集、禁用项和真实后端门禁；其中的厂商事实必须可追溯到第 2 项，不能覆盖与实物匹配的原厂资料。
4. 当前对外 JSON 线格式以 `contracts/vN/schemas/*.schema.json` 为准；本文规定 Schema 应如何设计、校验和演进。现有 Schema 若不符合本文，必须记录为差距并通过兼容变更或新版本修复，禁止在代码中自行重新解释线上格式。
5. 具体机器的设备地址、端口、通道和阈值以通过 Schema 校验的版本化部署配置为准。
6. 代码结构、命名、错误、日志和测试要求以本文为准。
7. 示例代码、测试辅助代码和历史实现不得反向覆盖以上规则。

引用以上权威文件时，应使用仓库内路径、具体章节，并在变更记录中保留对应 Git commit。权威文件本身发生变化时，必须重新检查受影响的代码、配置、Schema 和测试；无法消解的冲突必须阻止相关 real 能力启用并升级为待确认项。

若原厂资料之间相互冲突、型号不明或版本无法确认，必须保持 `UNCONFIGURED` 或配置值 `null`，并记录待确认项；禁止自行选择“看起来合理”的值。

## 4. 当前已经确立、必须继续遵守的规则

以下是当前仓库已经明确的边界，不是未来建议：

1. `snappy-control` 必须是 CAN、RS485、继电器和安全看门狗的唯一硬件写入进程。
2. `snappy-gateway` 禁止绕过 control 的状态机和互锁直接操作设备。
3. G20 UDP 是日常主力控制链路；EC20 MQTT/TLS 是辅助和人工应急接管链路。
4. 链路健康检测可以自动执行，但链路之间禁止自动接管；G20 失联后，MQTT 必须由操作者明确 `control.acquire`。
5. 当前活动链路失联时必须撤销 lease、清空待执行命令并进入 `SAFE_HOLD`；恢复连接不得自动续跑。
6. 4G 只使用 MQTT/TLS，禁止新增 WebSocket 控制链路。
7. 视频只允许走“RK USB 摄像头 → G20 SDK → Android”，禁止进入 MQTT、云端 collector 或 SQLite。
8. 未确认的 CAN ID、CAN 帧、RS485 站号/波特率/寄存器、继电器映射和 G20 SDK 参数必须保持未配置，禁止写死猜测值。
9. 默认构建必须关闭 real 后端：生产进程骨架注入 fail-closed 的 unconfigured 后端，模拟器和测试组合根注入 fake，并在无硬件环境完成整仓编译和契约测试。
10. 客户端自报的 `link_id` 不可信，gateway 必须按实际入口覆盖。
11. UDP 单消息上限为 1200 B 且禁止分片；UDS/MQTT 单消息上限为 64 KiB。
12. 代码变更必须在提交、代码评审或 CI 记录中附上实际验证证据；本地代理配置和工作日志不属于产品仓库内容。

## 5. 命名规范

### 5.1 通用命名

- 标识符必须表达业务或协议含义，禁止使用 `tmp1`、`data2`、`handleThing` 等无稳定语义名称。
- 缩写必须采用仓库统一形式：`Can`、`Rs485`、`Udp`、`Mqtt`、`G20`、`Ec20`。
- 设备逻辑 ID、配置键、JSON 字段和数据库字段必须使用 ASCII；中文名称只用于文档和面向操作者的显示文本。
- 一个概念必须只有一个规范名称。兼容旧名称时，应在边界层显式映射并标注弃用，禁止长期维护无记录别名。
- 布尔值应使用肯定语义，如 `healthy`、`ready`、`tls_required`；禁止双重否定名称。

### 5.2 C++

- 命名空间必须为 `snappy::<module>` 或其子命名空间。
- 类、结构体、类型别名和枚举类型必须使用 `UpperCamelCase`。
- 接口类必须使用 `I` 前缀，例如 `ICanBus`、`IRs485Bus`。
- 函数、参数和局部变量必须使用 `lower_snake_case`。
- 私有数据成员必须使用尾随下划线，例如 `health_`。
- 编译期常量和枚举值必须使用 `kUpperCamelCase`。
- 源文件和头文件必须使用 `lower_snake_case.cpp/.hpp`。
- 公共头文件必须通过 `snappy/<module>/...` 路径包含，禁止调用方依赖源码相对路径。
- 头文件必须使用 `#pragma once`，并直接包含自身声明所需的标准库头文件。
- `.cpp` 的 include 顺序应为：配对头文件、C/C++ 标准库、第三方库、项目头文件；各组之间空一行。
- 公共返回值若不可安全忽略，应使用 `[[nodiscard]]`。
- 简单谓词可以返回 `bool`；可能失败的 I/O、配置、解析和设备操作禁止只返回裸 `bool`。

### 5.3 Kotlin

- package 必须全小写并与目录和职责对应，例如 `snappy.remote.g20`。
- 类、接口、数据类和枚举类型必须使用 `UpperCamelCase`。
- 函数、属性和参数必须使用 `lowerCamelCase`。
- 常量必须使用 `UPPER_SNAKE_CASE`。
- 线协议枚举必须显式声明 wire value，不得依赖枚举名称的默认序列化。
- 可空字段必须对应契约中确实允许缺失或 `null` 的语义，禁止用可空性掩盖解析失败。
- 生产协议解析禁止使用正则表达式拼装 JSON 解析器。

### 5.4 Python

- 模块、函数、变量和参数必须使用 `snake_case`。
- 类和异常类型必须使用 `PascalCase`。
- 模块级常量必须使用 `UPPER_SNAKE_CASE`。
- 公共函数、方法和数据结构必须具有类型标注。
- 命令行入口文件可以使用连字符，例如 `snappy-cloudctl`；可导入模块必须使用下划线，例如 `snappy_cloudctl.py`。
- 仅表示调用方输入错误时可以直接使用 `ValueError`；设备、契约、存储和通信错误应使用有稳定 code 的领域异常或结果类型。

### 5.5 JSON、MQTT 与 SQL

- JSON 字段、配置键、MQTT topic 路径段、SQL 表名和列名必须使用 `lower_snake_case`。
- MQTT topic 必须使用既定层级：`snappy/vN/robots/{robot_id}/...`，禁止用 topic 大小写表达新语义。
- 状态、质量、严重性等闭集 wire 枚举必须使用 `UPPER_SNAKE_CASE`，例如 `SAFE_HOLD`、`GOOD`、`TIMED_OUT`。
- 链路 ID、设备 ID 等标识值必须使用 `lower_snake_case`，例如 `g20_udp`。
- 命令 action 必须使用 `<domain>.<verb>`，例如 `control.acquire`；同一动作禁止再定义下划线或连字符版本。
- Schema 必须默认 `additionalProperties: false`；扩展字段必须先更新 Schema 和兼容性说明。

## 6. 单位与数值命名

- 所有带单位的字段、配置键和非局部变量必须包含单位后缀。
- 时间持续量必须使用 `_ms`、`_us` 或 `_s`；时间戳必须明确是 epoch 还是单调时间。
- 内部超时、deadtime、age 和最大通电时长必须使用单调时钟；对外 `issued_at_ms`、`emitted_at_ms`、`received_at_ms`、`timestamp_ms` 使用 Unix epoch 毫秒。
- 长度和大小使用 `_mm`、`_m`、`_bytes`；速度使用 `_rpm`、`_mps` 或协议明确单位；百分比使用 `_pct`。
- 温度必须使用 `_celsius`，角度必须使用 `_deg` 或 `_rad`，角速度必须使用 `_deg_per_s` 或 `_rad_per_s`。
- 波特率使用 `baud_rate`，CAN 位率使用 `bitrate` 或 `bitrate_bps`，两者禁止混用。
- `baud_rate`（单位 baud）和既有配置中的 `bitrate`（单位 bit/s）是单位后缀规则的明确协议术语例外；除这两个已定义字段外，新增带单位字段仍必须使用单位后缀。若采用 `bitrate_bps`，必须通过版本化 Schema 迁移，禁止与 `bitrate` 长期并存。
- C++ 上层业务代码应使用 `std::chrono` 或强类型单位；裸整数只允许存在于协议编解码边界。
- 原始寄存器或帧值必须在设备驱动边界转换为有单位的领域值；控制层禁止自行重复缩放。
- 协议无法提供有效值时必须返回 `null`/`std::optional` 并设置质量，禁止使用 `0`、`-1` 或最大值充当“无数据”。

## 7. 分层与依赖

正式代码的依赖方向必须保持为：

```text
G20 UDP / MQTT / cloud / Android
              ↓
       snappy-gateway
              ↓  Unix SOCK_SEQPACKET
       snappy-control
              ↓
        设备领域抽象
              ↓
       设备协议编解码
              ↓
       CAN / RS485 / relay 总线
              ↓
        Linux/厂商 SDK 边界
```

- gateway 必须只处理网络、身份、契约、重放、心跳和 IPC，不得包含设备寄存器、CAN 帧或继电器通道。
- control 必须只依赖设备领域接口，不得在业务状态机中拼装原始 CAN/RS485 帧。
- 设备驱动必须负责设备动作、状态、缩放、有效范围和协议响应语义。
- 单帧协议编码、校验和解码函数必须无 I/O、可重复调用。多帧重组器可以保存必要状态，但必须与文件描述符和业务状态机分离。
- 总线层必须负责文件描述符、收发、传输帧边界、deadline 和总线互斥，不得包含设备业务动作。Modbus CRC、设备专用 checksum 和协议字段校验属于 `protocols/` 中的共享或设备 codec；总线层只报告系统 I/O、长度和传输状态，禁止复制一套协议校验。
- 厂商 SDK 必须由适配器封装；厂商类型和全局状态禁止泄漏到 control 或 gateway。
- production 目标禁止依赖 `simulator/`；fake 只能在测试、模拟器或组合根中注入。
- 云端和 Android 代码禁止依赖 RK3588 设备驱动实现。

## 8. 目录与文件结构

### 8.1 现有顶层结构

现有顶层职责必须保持：

```text
contracts/          对外契约与跨语言测试向量
rk3588/control/     控制生命周期、安全和设备领域调用
rk3588/gateway/     G20/MQTT/IPC 边界
rk3588/drivers/     总线、协议和真实/unconfigured 设备实现
rk3588/config/      版本化配置示例及配置 Schema 的目标位置（当前尚未建立 Schema）
remote/android/     Android/G20 协议和适配器
cloud/              MQTT collector、CLI、SQLite 和 broker 配置
simulator/          fake 实现与端到端模拟
deploy/             systemd、broker 等部署模板
exa/                本地 Git 忽略的原厂资料区，不属于产品仓库或正式构建
tools/              可重复的构建、测试和检查入口
```

### 8.2 新设备驱动结构

新增真实设备驱动必须完成总线、协议和设备职责拆分；下列具体目录树为推荐布局，采用其他布局时必须保持同等依赖边界并在评审中说明：

```text
rk3588/drivers/
├── include/snappy/drivers/
│   ├── bus/
│   ├── protocols/
│   └── devices/
├── src/
│   ├── bus/
│   ├── protocols/
│   └── devices/
├── tests/
│   ├── protocols/
│   ├── devices/
│   └── hil/
└── CMakeLists.txt

simulator/fake-hardware/
├── include/snappy/simulator/fakes/
└── src/fakes/
```

- 一个物理设备型号或一个共享协议组件应对应一组清晰命名的 `.hpp/.cpp`。
- `bus/` 只放 SocketCAN、串口和事务调度；`protocols/` 只放帧、CRC、寄存器和 codec；`devices/` 只放物理量、状态与设备语义；fake 放在 `simulator/.../fakes/`，禁止混入 real 目录。
- 公共接口与私有实现必须分离；仅供实现使用的头文件不得安装为公共 include。
- 驱动测试必须按 `tests/protocols`、`tests/devices`、`tests/hil` 分层；文件必须以 `_test.cpp`、`test_*.py` 或 Kotlin 对应测试命名结尾。
- 复杂设备可以使用子目录；简单设备不应为追求目录层级而拆成大量单行文件。
- CMake library target 必须以 `snappy_` 开头并使用 `snake_case`；最终进程名使用连字符，例如 `snappy-control`。
- 新真实驱动可以逐步迁移现有平铺骨架；禁止仅为目录美观进行与功能无关的大规模搬迁。

### 8.3 Kotlin、Python、契约与 SQL 文件

- Kotlin production 源码必须位于对应模块的 `src/main/kotlin/<package>/`，测试位于镜像 package 的 `src/test/kotlin/<package>/`。
- Python 可导入代码必须位于包目录，测试统一使用 `test_*.py`；命令行连字符入口只作薄包装，业务逻辑必须留在可导入模块中。
- Schema 文件必须命名为 `<kind>.schema.json`；测试向量必须命名为 `<kind>.valid.<case>.json` 或 `<kind>.invalid.<case>.json`，简单基线可以省略 `<case>`。
- 每个契约版本必须有 manifest，且只引用同版本的 Schema 和向量。
- SQLite 初始结构保留在 `cloud/schema.sql`；未来增量迁移应放入 `cloud/migrations/`，命名为四位递增序号加描述，例如 `0001_add_event_index.sql`。已部署迁移禁止原地改写。
- SQL 索引、唯一约束、检查约束、外键、触发器和视图应分别使用 `idx_`、`uq_`、`ck_`、`fk_`、`trg_`、`v_` 前缀，并继续使用 `lower_snake_case`。

## 9. 总线通信与并发

### 9.1 通用要求

- 每个物理总线或文件描述符必须只有一个明确 owner；多个设备禁止并发直接读写同一 fd。
- 总线访问必须通过有界请求队列或单线程事件循环串行化。
- 每次 I/O 必须有单调时钟 deadline；禁止无限阻塞。
- 请求队列必须定义容量、满队列策略和优先级；安全停止必须高于普通命令。
- 禁止 detached thread、无界队列和无法取消的后台任务。
- 锁的作用域内不应执行可能无限等待的系统 I/O；多锁场景必须记录并遵循固定加锁顺序。
- stop、关闭和析构必须能够打断或终止待处理 I/O，不得依赖进程强杀完成资源释放。
- 自动重试只允许用于明确幂等的操作；每种操作必须定义最大次数、退避和总 deadline。
- 启动、运动、继电器通电、地址修改、波特率修改等写操作禁止无条件自动重试。
- 通信接口应携带 operation、device ID、deadline 和关联 ID；禁止仅靠自由文本判断响应归属。

### 9.2 CAN

- CAN ID、标准/扩展帧、DLC、字节序、缩放、枚举和值域必须由具名常量或类型表达。
- 经典 CAN 和 CAN FD 必须显式区分；payload 容器必须有协议允许的上限。
- 接收帧必须校验 ID、帧类型、DLC 和设备状态字段后才能更新 actual state。
- CAN 心跳、在线状态和样本 freshness 必须与“最近成功发送”区分。
- 帧常量必须注明原厂资料版本和章节；禁止在业务代码中出现无说明十六进制 magic number。

### 9.3 RS485

- RS485 端口必须具名配置，禁止依赖数组下标表达物理含义。
- 串口参数必须完整包含设备路径、波特率、数据位、校验位、停止位和必要的流控设置。
- 同一端口上的交易必须串行执行，并在发送前清理或识别陈旧输入。
- Modbus RTU 或自定义帧响应必须校验站号、功能码、长度、CRC、异常码及写响应 echo。
- 设备驱动负责寄存器与领域值映射；共享 Modbus 组件负责通用帧和 CRC。
- 广播写、修改站号、修改波特率和恢复出厂必须是独立维护操作，禁止出现在正常控制循环中。
- 读超时、CRC 错误、地址不匹配和设备异常响应必须使用不同稳定错误 code。

### 9.4 继电器与推杆

- control 和设备层只能使用逻辑通道；物理通道映射只能来自配置。
- 同一推杆的伸出和缩回输出必须硬性互斥。
- 换向必须先全部失电，等待配置的 deadtime，再允许反向通电。
- 每次通电必须有本机最大持续时间，使用单调时钟强制截止。
- 无到位反馈时，终态只能表示 `ASSUMED_REACHED`，禁止表示真实到位。
- `deenergize_all` 必须幂等，并在任何启动失败、通信故障、进程停止或安全保持路径中可调用。

### 9.5 传感器

- 每个进程内样本必须包含规范逻辑名、领域值、单位、质量和采样单调时间；内部 freshness 判断只能基于该单调时间。
- 对外 JSON 快照必须输出接收方可直接使用的 `age_ms`，不得跨进程传递或比较不同启动域中的单调时钟时间点。
- CRC 错误、范围错误、超时和陈旧值必须分别映射为 `INVALID`、`STALE` 或设备 fault，禁止继续标记为 `GOOD`。
- 最近一次好值可以用于诊断显示，但不得在安全判断中伪装成当前好值。
- 传感器量程、缩放、偏移和安装方向必须来自已确认资料或配置。

## 10. JSON、MQTT、UDP 与 IPC 契约

### 10.1 单一事实来源

- `contracts/vN/schemas/*.schema.json` 必须是对外 JSON 结构的唯一事实来源。
- C++、Kotlin 和 Python 模型必须显式映射 wire 字段，禁止依赖各语言默认字段名或枚举序列化。
- Schema 变更必须同步更新有效和无效 golden vectors，并在三种语言中验证。
- 生产解析不得使用只覆盖少数字段的手写正则或“只检查 `kind`”的替代校验。
- Schema 允许的 `null`、必填字段、最大长度、数值范围和 `additionalProperties` 必须全部执行。

### 10.2 入站 command 校验顺序

所有经 G20、MQTT 或 gateway-to-control IPC 进入的 command 必须按以下顺序处理；非 command 消息只执行其 Schema、身份和传输边界适用的步骤，不执行 lease/action 校验，也不生成命令 ACK：

1. 检查传输层大小限制；
2. UTF-8 和 JSON 解析；
3. 按 `schema_version` 选择并执行完整 Schema；
4. 对 MQTT 校验认证身份、topic 中 robot ID 与 payload `robot_id` 一致；对无 topic 的 UDP/IPC 校验其已认证 peer 或受信 IPC 身份；
5. 网络入口由 gateway 按实际 transport 覆盖 `link_id`；control 对 IPC 中缺失或未知的规范化 `link_id` 必须拒绝；
6. 校验 `boot_id`、`session_id`、`seq`、`issued_at_ms`、`ttl_ms`；
7. 校验 `control_epoch`、`lease_id` 和当前 lease owner；
8. 执行动作级权限、安全状态和值域校验；
9. 调度，并只通过请求进入时对应的已认证返回路径生成引用原 `message_id` 的 ACK；禁止自动镜像到另一链路。state、event、telemetry 和 presence 可按发布策略独立发送到已连接链路。

任一步失败均禁止进入设备执行层，并应返回稳定错误 code 或记录可诊断事件。

### 10.3 重放、超时与主题

- 重复、乱序、过期、旧 boot、旧 session、旧 epoch 和旧 lease 命令必须拒绝且不得重复执行。
- `link_id` 必须由实际 transport 决定。
- MQTT topic 中的 `{robot_id}` 必须与消息和认证身份一致。
- 命令、ACK 和事件使用 QoS 1、`retain=false`；遥测使用 QoS 0。
- MQTT 客户端必须禁用离线命令排队和重连后旧命令补发。
- UDP 禁止应用层分片；需要超过 1200 B 的数据不得通过 G20 命令数据报发送。
- 视频没有 MQTT、collector 或 SQLite topic；禁止新增 `up/video` 等入口。

### 10.4 兼容性

- v1 内禁止无版本号的破坏性字段修改。
- 新增可选语义也必须先更新 Schema、vector 和各端解析器。
- 破坏性变更必须创建新的版本目录和 topic 版本，例如 `contracts/v2`、`snappy/v2/...`。
- MAY：从 Schema 生成部分模型或校验代码，但生成产物必须可重复并接受相同测试。

## 11. 配置规范

- 所有部署配置必须有 `schema_version`，并通过对应 JSON Schema 校验。
- 配置 Schema 必须拒绝未知字段、错误类型、非法范围和重复物理资源映射。
- 配置请求 `backend: "real"` 时，任何必需总线参数、设备地址、`protocol_profile`、继电器映射或安全阈值缺失都必须使组合根不构造、不启动 real adapter，而改为注入 `Unconfigured...` 边界；该边界对外暴露生命周期 `UNCONFIGURED`。control 可以以诊断/安全模式运行，但必须拒绝 arm，且禁止访问不完整配置对应的设备节点。
- real 配置失败禁止静默回退到 fake。
- fake 模式不得读取或要求真实硬件参数。
- 未确认值必须为 `null` 或明确缺失，禁止填入厂商默认值假装已确认。
- 物理资源必须使用具名对象；禁止通过数组位置隐式表示“第几路串口”或“第几路继电器”。
- 配置必须分别使用 `protocol_family` 表达协议族（例如 `modbus_rtu`），使用 `protocol_profile` 表达型号/修订专用映射（例如 `bd201s_v25`）；禁止用含糊的 `protocol` 或 `frame_profile` 同时承担两种语义。
- 物理资源冲突必须按作用域判定：CAN 使用 `(interface, can_id)`，RS485 使用 `(port, station_id)`，继电器使用 `(controller_id, physical_channel)`；同一作用域内被不兼容设备重复占用时，配置加载必须失败。
- 安全阈值必须注明单位并设置本机上限；远端命令不得任意放宽。
- TLS 私钥、密码和 Token 必须由独立凭据机制提供，禁止写入仓库配置、日志或测试向量。
- 配置加载应在启动阶段原子完成。MAY：未来支持热更新，但总线、映射或安全参数变更必须先进入安全状态并重新自检。

## 12. 错误与健康模型

### 12.1 错误结果

可能失败的驱动和通信操作必须返回结构化结果。结果至少应包含：

- 稳定 `code`；
- `device_id` 或 component；
- `operation`；
- 是否允许重试；
- 面向人的 `detail`；
- 必要时包含底层错误类别或原始系统错误码。

稳定 code 必须使用 `UPPER_SNAKE_CASE`，例如：

- `CONFIG_REQUIRED`
- `CAN_TX_TIMEOUT`
- `CAN_FRAME_INVALID`
- `RS485_TIMEOUT`
- `RS485_CRC_MISMATCH`
- `RS485_ADDRESS_MISMATCH`
- `RELAY_INTERLOCK_ACTIVE`
- `SENSOR_STALE`
- `LEASE_EXPIRED`
- `SAFE_HOLD_ACTIVE`

`detail` 可以改进措辞，自动化逻辑禁止解析 `detail`；自动化只能依赖稳定 code 和结构化字段。

### 12.2 健康维度

以下维度必须分开建模，禁止压缩为一个模糊 `ok`：

- 生命周期：`UNCONFIGURED`、`STOPPED`、`STARTING`、`READY`；
- 设备健康：`GOOD`、`DEGRADED`、`FAULT`；
- 样本质量：`GOOD`、`STALE`、`INVALID`、`UNKNOWN`；
- 链路健康：`UP`、`DEGRADED`、`DOWN`、`UNKNOWN`；
- 控制状态：架构定义的 `BOOT`、`SELF_TEST`、`DISARMED`、`ACQUIRED`、`ARMED_IDLE`、`ACTIVE`、`SAFE_HOLD`、`FAULT_LATCHED`、`ESTOP_LATCHED`。

健康快照应包含最近成功时间、连续失败次数和最后错误；“进程活着”不等于“设备健康”。

每个驱动必须在设备规范中定义转换算法、latch/clear 条件和必需配置键；具体数值可以由带来源、单位和 HIL 记录的部署配置提供。所有实现至少遵守以下公共转换：

- 配置不完整：生命周期保持 `UNCONFIGURED`；
- 配置完整但未启动：`STOPPED`；
- 启动中：`STARTING`；
- 自检和通信建立成功：`READY + GOOD`；
- 可恢复的间歇错误达到设备阈值：`READY + DEGRADED`；
- 不可恢复错误、安全关键错误或连续失败达到 fault 阈值：健康维度进入 `FAULT`；若总线仍可用于诊断，组合为 `READY + FAULT`，若驱动必须关闭则组合为 `STOPPED + FAULT`，具体选择由设备规范和安全状态机规定；
- 从 `DEGRADED` 恢复必须满足设备规范规定的连续成功条件，禁止单次成功立即清除抖动故障；
- latched fault 只能通过明确 reset、重新自检并满足安全条件后清除。

`safe_stop()` 表示把执行器输出带到安全状态，不必关闭仍用于诊断的总线；`stop()` 才表示停止驱动生命周期。两者的状态变化必须分别记录和测试。

### 12.3 异常边界

- C++ 驱动接口禁止让异常跨越总线 worker 或 control 主循环边界；必须转换为结构化错误。
- `noexcept` 函数内部必须捕获或避免会抛出的操作。
- Python CLI 可以在最外层把领域异常转换为非零退出码和简洁错误信息。
- 解析、存储或第三方 SDK 异常必须在所属边界转换，不得导致安全停止路径被跳过。

## 13. 日志规范

- 进程日志必须结构化，并输出到 stdout/stderr 供 journald 接管；禁止手工拼接未转义 JSON。
- 每条设备或通信日志应包含：`timestamp_ms`、`severity`、`process`、`component`、`device_id`、`operation`、`code`。
- 命令链路日志还应包含适用的 `message_id`、`session_id`、`control_epoch`、`link_id`。
- 日志时间必须明确使用 UTC epoch；超时诊断可以附带单调持续时间。
- 禁止记录密码、Token、私钥、完整证书或敏感认证头。
- 原始帧和完整 payload 默认不得在 INFO 级别输出；调试输出必须受限、可关闭并进行长度截断。
- 高频 CRC、超时和断链日志必须限流，同时保留累计计数和首次/最近发生时间。
- 安全状态变化、lease 变化、arm、stop、fault latch 和配置拒绝必须记录不可歧义的事件。
- 日志失败不得阻塞安全停止或总线控制主循环。
- `snappy-cloud-collector` 必须把结构化日志输出到 journald，并按部署配置提供滚动文本日志；两种输出必须共用相同字段和脱敏规则。

## 14. 注释与协议溯源

- 正式代码标识符和代码注释必须使用英文；规范、设备说明和运维文档可以使用中文。
- 注释必须解释原因、风险、单位、边界或协议依据，禁止逐行复述代码。
- 每组寄存器、CAN 帧、功能码、缩放、CRC 特例或状态位必须注明：
  - 设备厂家和型号；
  - 原厂资料文件名；
  - 资料版本或日期；
  - 页码、章节或表格；
  - 字节序、符号、缩放和单位。
- 若使用原厂 SDK，必须记录 SDK 来源、版本和本地封装边界。
- 未确认参数使用 `TODO(protocol-confirmation)` 或等价明确标记，并关联到设备规范中的待确认项；禁止普通 `TODO` 隐藏安全或协议缺口。
- 注释中的示例帧必须由测试向量覆盖，避免文档与实现漂移。
- 修改协议常量时必须同步检查设备规范、配置示例、测试向量和相关日志字段。

## 15. 安全停止与执行器规则

- 每个执行器驱动必须在设备规范中定义可验证的安全状态，而不是只提供泛化 `stop()` 名称。
- `safe_stop()`、`stop()` 和 `deenergize_all()` 必须幂等、可重复调用，并且不得抛出异常。
- 安全停止必须尽最大努力作用于所有已初始化设备；一个设备失败不得阻止其他设备进入安全状态。
- 安全停止路径不得依赖云端、Android、MQTT 可用性或新 lease。
- 配置缺失、总线故障、传感器无效/陈旧、lease 过期、gateway/control 心跳超时和进程退出必须进入本机安全处理。
- 推杆和方向继电器必须先失电、执行 deadtime、再反向；最大通电截止必须由本机单调时钟保证。
- 无反馈执行器的位置状态只能报告 `UNKNOWN`、`MOVING_EXTEND`、`MOVING_RETRACT` 或 `ASSUMED_REACHED`；故障必须另由设备健康的 `GOOD/DEGRADED/FAULT` 表达，禁止伪造实际到位或把两个维度压成一个枚举。
- ACK `ACCEPTED` 只表示命令进入本机处理，不表示动作已完成；实际结果必须通过后续 ACK/state 表达。
- 活动链路失联后必须撤销 lease、取消待执行命令并进入 `SAFE_HOLD`；另一链路禁止自动接管。
- real 配置或安全阈值不完整时必须禁止 arm，但不应阻塞 fake 构建和测试。
- SHOULD：安全关键路径避免动态分配、长时间锁和非必要日志格式化。

## 16. fake、real 与 unconfigured 后端

### 16.1 共同要求

- 三种后端必须实现相同的稳定接口和状态语义。
- 业务逻辑必须通过依赖注入或组合根选择后端，禁止在控制状态机中散布 `#ifdef FAKE`。
- fake 和 real 必须保持公共接口、值域、错误分类、控制可见状态和安全语义一致；真实时序、噪声和读回值可以不同，fake 无需假装精确物理模型。

后端选择必须遵守以下组合边界：

| 组合根 | 允许后端 | 禁止行为 |
|---|---|---|
| `snappy-control` / `snappy-gateway` 生产进程 | 配置完整且通过门禁的 real；否则 unconfigured | 禁止链接或运行时加载 `simulator/`，禁止 real 失败后回退 fake |
| `snappy-sim`、单元测试、契约测试 | 显式 fake，可混合 unconfigured 做拒绝测试 | 禁止访问真实设备节点或生产凭据 |
| Android 缺闭源 G20 AAR 的构建 | `NullG20Adapter` | 禁止把 null adapter 报告成链路或设备成功 |
| 显式 commissioning/maintenance 工具 | 输出受抑制、操作者确认的受限 real adapter | 禁止作为生产控制循环自动启动或使用 wildcard 扫描共享总线 |

配置中的逐设备 `backend` 只能选择该组合根已注册的允许实现；它不是在生产进程中动态加载 fake 库的许可。

### 16.2 fake

- fake 必须 deterministic；相同初始状态和输入必须产生相同输出。
- fake 必须支持注入正常响应、超时、CRC/帧错误、断链、stale、fault 和恢复。
- fake 不应依赖真实 sleep；时间行为应通过可控时钟推进。
- fake 必须记录可断言的命令、帧、请求、状态和安全停止调用。
- fake 可以简化物理模型，但禁止无条件成功到无法覆盖错误路径。

### 16.3 unconfigured

- unconfigured 表示真实后端边界存在但资料或配置不足。
- unconfigured 的启动和 I/O 必须 fail closed，返回稳定 `CONFIG_REQUIRED` 或等价错误，并保持 `UNCONFIGURED`。
- unconfigured 禁止访问真实设备节点、发送网络包或模拟成功。
- unconfigured 与 fake 禁止共用“成功”行为。

### 16.4 real

- real 后端只有在配置完整、协议来源明确且自检通过时才能进入 `READY`。
- real 后端禁止包含来源不明的站号、波特率、CAN ID、寄存器、通道或安全阈值。
- real 初始化失败禁止回退到 fake；必须暴露错误并阻止 arm。
- 第三方 SDK 缺失时，可以不构建对应 real adapter，但公共接口和 fake 测试必须继续可用。

## 17. 测试与合并门禁

### 17.1 分层最低测试

测试要求按本次交付实际包含的层级适用；接口骨架禁止为了满足测试清单而虚构尚未确认的帧、寄存器或缩放。

- 接口骨架必须覆盖：缺失配置 fail closed、fake 正常/失败路径、生命周期 `start()`/`stop()`/重复 `stop()`、`safe_stop()`、适用的运动取消动作和依赖注入。
- 协议 codec 存在时必须覆盖：编码/解码 golden vectors、最小/最大/越界、符号/缩放、短帧/超长帧、错误 ID/地址/功能码、CRC 和异常响应。
- 总线 worker 存在时必须覆盖：I/O 超时、deadline、取消、有限重试、并发串行化、队列满和安全停止优先级。
- 设备状态实现存在时必须覆盖：health、quality、fault、latch/clear、日志和稳定错误 code。
- real adapter 存在时必须使用同一公共契约测试，并按 17.4 提供硬件验证后才能声明真实支持。

共享 codec 应使用纯单元测试。MAY：对复杂 codec 增加属性测试或 fuzz 测试。

### 17.2 跨语言契约测试

- command、ack、state、telemetry、event、presence 每种 Schema 必须至少有有效和代表性无效向量。
- manifest 中每个向量必须由 C++、Kotlin 和 Python 验证。
- 必须验证必填字段、未知字段、长度、枚举、数值上下界和 `null` 语义。
- gateway、cloudctl、collector 和 Android/G20 适配器生成或接收的消息必须通过同一 Schema。
- 禁止以三端各自复制的部分校验逻辑替代 Schema 一致性测试。

### 17.3 仓库门禁

合并前必须至少执行并记录：

```bash
./tools/test-all.sh
./tools/run-fake.sh
```

当前自动化尚未提供统一 formatter/linter 配置，因此现阶段合并还必须执行 `git diff --check`、编译和本节已有测试，且禁止声称“格式化/静态分析已通过”。下列工具化门禁是明确目标，最迟必须在第一个 real 后端启用或声明支持前提交仓库级配置并执行：

- C++ formatter、编译告警检查和适用的 sanitizer；
- Python formatter、lint 和类型检查；
- Kotlin formatter 和静态检查；
- JSON/JSON Schema、SQL 和 shell 静态检查；
- 无真实硬件、无闭源 SDK 环境下的全 fake 构建。

目标工具应为：C++ 使用仓库 `.clang-format` 与 clang-tidy/编译告警配置；Python 使用仓库统一的 Black、Ruff 和类型检查配置；Kotlin 使用 ktlint 或等价仓库配置；shell 使用 shfmt 与 ShellCheck；JSON/Schema/SQL 使用固定版本校验器。配置文件一旦提交，对修改范围即成为 MUST 门禁。在此之前，工具缺失属于第 19 节差距，不豁免本文已经可人工判定的命名、类型、安全、依赖和契约规则。

编译告警不得作为“已知可忽略”长期积累；确需抑制时必须局部、注明原因并可追溯。

### 17.4 硬件验证

- fake 测试通过只证明软件契约，不证明真实设备可用。
- 声明某 real 驱动“支持”或“完成”前，必须提供对应型号和资料版本下的 hardware-in-the-loop 证据。
- 硬件验证必须记录配置、设备型号/版本、命令、读回值、故障注入和安全停止结果。
- 未执行硬件验证时必须明确标注“未做硬件确认”，不得用模拟结果替代。

## 18. Definition of Done

设备或协议工作只有在对应层级全部满足时才可声明完成。

### 18.1 接口骨架完成

- [ ] 公共接口、fake 和 unconfigured 实现可编译；
- [ ] 未确认真实参数保持 `null`/`UNCONFIGURED`；
- [ ] fake 正常与失败路径有测试；
- [ ] 不存在对真实硬件的隐式访问；
- [ ] `./tools/test-all.sh` 和 `./tools/run-fake.sh` 通过；
- [ ] 提交、代码评审或 CI 记录包含目标、验证证据和剩余限制。

接口骨架完成不等于真实协议或设备驱动完成。

### 18.2 已批准协议子集实现完成

- [ ] 型号、手册版本、页码/章节可追溯；
- [ ] 声明的 `protocol_profile` 和已批准子集内所有帧、寄存器、CRC、缩放、单位和值域有具名实现；
- [ ] 已批准子集的 codec golden vectors 和错误向量完整，规范明确禁用的命令/帧会被显式拒绝；
- [ ] 配置 Schema 已覆盖所需参数；
- [ ] 结构化错误、健康状态和日志已实现；
- [ ] `safe_stop()`、超时、重试和并发语义有测试；
- [ ] 相关设备规范、配置和契约无冲突。

协议实现完成仍不等于硬件验证完成。

### 18.3 真实设备 HIL 支持完成（`hil_qualified`）

本层完成只允许声明特定 `model` / `protocol_profile` 通过设备级 HIL；生产 `arm` 还必须满足设备驱动规范定义的 `deployment_qualified` 集成门禁。

- [ ] real 后端只使用已确认配置，缺失时 fail closed；
- [ ] 在目标 RK3588、目标总线适配器和对应设备型号上完成联调；
- [ ] 正常控制、状态读回、断链、超时、异常帧和恢复均有证据；
- [ ] 按设备类型适用的安全停止、失电、互锁和最大动作时长完成故障注入；
- [ ] fake 与 real 的公共接口、值域、错误分类、控制可见状态和安全语义符合 16.1；真实时序、噪声和读回差异已有记录；
- [ ] 文档明确仍存在的硬件限制和风险；
- [ ] 验证结果已写入提交、代码评审或 CI 记录。

### 18.4 变更交付完成

- [ ] 仅修改任务所需范围，未混入无关重构；
- [ ] 代码、配置、Schema、测试和文档同步；
- [ ] 没有凭猜测加入硬件参数；
- [ ] 没有敏感凭据、生成数据库、class/jar 或临时验证文件进入 Git；
- [ ] 所有实际执行的检查及其结果已如实报告；
- [ ] 未运行的 HIL、部署或安全测试已明确说明，禁止笼统声称“全部验证通过”。

## 19. 当前差距清单

本节记录审计时仓库尚未达到本文目标规则之处。这些内容是待办和风险说明，不表示已经实现。

1. **设备逻辑名尚未统一。** 配置使用 `lower_snake_case`，部分 C++ 测试仍使用 `logical-sensor`、`brush-lift-up`、`wind-speed`、`squeegee-up`。
2. **契约校验仍是部分实现。** gateway 目前只检查 JSON object、`schema_version` 和 `kind`，尚未执行完整 command Schema、topic/robot 一致性、重放、TTL、epoch 和 lease 校验。
3. **跨语言向量覆盖不完整。** 当前 manifest 只覆盖 command、ack、state，event、presence、telemetry 尚无完整有效/无效向量；C++ 与 Kotlin 也只是部分字段检查。
4. **Kotlin 测试解析器不是正式 JSON 实现。** 当前 golden test 使用正则提取字段且未覆盖完整 `params` 和未知字段语义，只能视为骨架验证。
5. **collector 尚未按 Schema 验证消息。** 当前主要检查 topic、大小、`robot_id` 和 `kind`，测试仍允许不完整 state/ack。
6. **错误模型过弱。** 当前 C++ `drivers::Result` 只有 `ok` 和自由文本 `detail`，gateway `PumpResult` 也依赖布尔值和字符串，尚无稳定错误 code、operation 或 retryable 字段。
7. **健康状态转换尚未统一。** 当前代码未明确区分 `safe_stop` 与生命周期 `stop`；设备健康也尚无 `DEGRADED`、转换阈值及最近成功/连续失败信息。
8. **已有真实硬件配置、Schema 和运行时 loader；`hardware.example.json` 仍只用于示例和模拟。
9. **真实设备真实设备已经按总线、协议和设备层拆分，但仍需完成全部 HIL 验收。
10. **RS485 已按物理端口串行调度；CAN 使用 SocketCAN，仍需验证长期总线故障恢复。
